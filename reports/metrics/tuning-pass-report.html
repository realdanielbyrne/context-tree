Closing report of the four-dimension tuning pass

Context-tree evaluation program · DS-STAR pass, iterations 1–3 · September 2, 2026 · commit 77d5326

Who this is for. This is the handoff document for the next agent picking this work up with no memory of the pass. It states what is settled and with which number, what is dead and must not be re-run, what the pass learned about its own instruments, where the code stands by path, and what to do next in order. It is written to be consistent with reports/algorithm.md, which remains the reference description of the algorithm and the document the next agent should edit alongside any change. Where this report and that page disagree, that page is authoritative on the algorithm and this one is authoritative on what was measured in this pass.

Abstract

Context-tree rewrites an agent's linear conversation into a summary-headed tree: completed stretches of work become short summaries in the prompt while the raw events stay on disk behind four retrieval tools. This pass ran three DS-STAR iterations to establish, by measurement, the four settings the algorithm leaves open — visible branch count, branch depth, summary timing, caching. Iteration 1 analysed artifacts already on disk and produced knowledge, not improvement; iterations 2 and 3 ran seven offline experiments at zero model calls. Two dimensions closed. The summary-timing gate lags one turn, overshooting its threshold by a median 8,306 tokens across six live crossings (n=6, claude-sonnet-5), and replays same-turn at a median 0. The cache simulator, once its matching rule was corrected, reversed its own verdict on a third cache breakpoint from +23% to −39.8% session cost on one 754-turn fixture, agreeing in sign with a live run at −18% cost per turn (n=5). Two did not close: branch count and depth are blocked behind a retrieval floor of 4 successes in 120 searched rows, not behind spend. The pass refuted more than it confirmed, including three claims the reference description carried. Main limitation: one frozen store, one scenario pair, one model family.

1 Terms

A turn is one model call. A run is one arm attempting one question or scenario once; a replicate is one run within a cell and n is the number of replicates. An epoch is a batch of runs made in one sitting against one build, so two arms compared inside an epoch saw the same code, task material and model snapshot. An arm is one configuration under test; a baseline is the arm it is paired against.

A branch (a phase node in the code) is context-tree's unit of summarization: a contiguous range of the append-only event log that receives one summary. The prompt is assembled in three fixed sections — Zone A, the frozen contract; Zone B, the root index plus branch summaries in creation order; Zone C, the active branch's raw detail — and retrieved results append after Zone C. W is the model's context window. The fold level (rootKeep) is how many of the most recent branches get an individual headline line in the root index before older ones fold to one line; a rendered body (branchesSurviving) is a branch whose full summary block renders separately in Zone B. The two move in opposite directions because both are paid out of one Zone B allowance. A rung is one entry on the fold ladder [40,16,12,8,6,4,2].

The switch point is the prompt size at which the tree stops showing the whole raw trace and starts showing summaries; the latch is the rule that once crossed, it never reverts. A cache read is a prompt token the provider served from a stored prefix; a cache write is one it had to store fresh. A breakpoint is a cache_control marker telling the provider where a cacheable prefix ends. Exact tokens means the cl100k BPE count; heuristic tokens means the assembler's own estimator, which over-counts real BPE by about 1.18× on this corpus. A stratum is one of the four question types on the frozen fixture: head (a fact from early in the session), tail (a recent fact), deep (a verbatim code literal), spanning (a fact requiring two places at once).

Metrics throughout are tokens, turns, graded score and success counts. Scores are means, tokens and turns are medians. Every figure pairs a candidate against a baseline at the same model and the same epoch. Dollar figures appear only in the footnote, beside the baseline they are relative to.

2 What this pass set out to do, and how the three iterations actually ran

reports/algorithm.md states four rules the algorithm is scored against: no budgets or caps; a hardcoded value is a defect unless it has been shown to hold off the host it was fitted on; setting a parameter from a model's limits is fine but guessing it is not; and prefer finding the sweet spot to picking a bound. It then names four dimensions where a real tradeoff exists and the winning setting has never been established — visible branch count, branch depth, summary timing, caching. This pass's objective was to establish those settings by measurement, scoped against the constant-and-boundary audit in eval/plans/portability-audit/, whose headline finding frames everything below: packages/core had no representation of the host's window size anywhere, so every value the tier-2 table says should be a fraction of W was a plain integer literal because there was nothing in the library to divide by.

2.1 Iteration 1 — analysis only, and it produced knowledge rather than improvement

Four analyses, one per dimension, at zero model calls: eval/plans/tuning/0{1,2,3,4}-*.md, published as four reports under reports/metrics/tuning-*.md. No configuration changed and no arm was run. What the iteration bought was a corrected framing, and the corrections were larger than any tuning result in the pass:

  • Two different counts had been conflated. The fold level and the number of rendered summary bodies are different numbers moving in opposite directions, and the two shipped arms differ in which of them they maximise.
  • “Width helps” was too broad. The effect holds on one stratum of four, and on the tail stratum both non-tree baselines beat both tree widths.
  • Depth is not a decision anybody made. It is whatever the tool-name-to-phase map and the neutral-merge rule produce from a trace — on the one measured store, a 77-fold spread across 21 branches.
  • The switch point's target is the Zone C fraction by the rule's own wording, and the two harnesses had drifted apart on it (0.35 against 0.20 for one quantity).
  • A cache write costs 12.5 times a cache read per token, which settles that prefix size is not what decides the caching question.

The four published reports also re-derived every load-bearing figure from the artifacts and found six figures in dimension 1's own analysis, seven in dimension 2's and nine in dimension 3's that did not reproduce as written. That auditing habit — publish the reproduction, not the note — is what made iterations 2 and 3 possible, and it is the single practice most worth carrying forward.

2.2 Iteration 2 — four offline experiments plus a judge

Four experiments (eval/plans/tuning/exp-0{1,2,3,4}-*.md), four new scripts under eval/scripts/, zero model calls, then an independent judge pass that re-ran every script and re-read every cited artifact at its anchor (ITERATION-2-VERDICT.md). Three of the four scripts reproduced to the token; the fourth did not, for a reason that turned out to matter more than the experiment (§5.4). The iteration refuted more than it confirmed, including three claims reports/algorithm.md was carrying at the time.

2.3 Iteration 3 — three follow-ups, each forced by iteration 2's dependency order

Three tasks, again at zero model calls: 3-A validated the cache simulator against an already-published live run and re-decided the third breakpoint (exp3-a-simulator-fidelity.md); 3-B re-measured branch sizes after the double-render fix landed, crossing both segmentations with both renderer states (exp3-b-branch-sizes.md); 3-C decomposed the run-level token gap between the two width arms bucket by bucket (exp3-c-width-attribution.md). Two produced a result; the third produced a demonstration that its question cannot be answered at the n available.

Across all three iterations: zero live model calls were made by any experiment. Every live number in this report was already on disk when the pass started.

3 Conclusions per dimension

3.1 Visible branch count — the mechanism is settled; the default is not, and the score floor blocks deciding it

Settled: there is no third allocation mechanism to build. Rendered bodies are monotone non-increasing in the fold level. Walking every rung at every window through the real assembler gives, at W=32,768, bodies 0 / 2 / 5 / 6 / 8 / 10 / 11 at rungs 40 / 16 / 12 / 8 / 6 / 4 / 2. So “walk toward maximising rendered bodies subject to the same fits predicate” always selects the ladder's smallest rung, which is exactly where the reversed-ladder arm tree-wide already stops. The two shipped arms are the two ends of one monotone curve. Reproduced by this report by re-running eval/scripts/ladder-curve.mjs: every cell identical.

Settled: the fit predicate barely binds. Six of the seven rungs satisfy it at W=32,768, so the hand-picked ladder direction, not the mechanism, picks the allocation. And the band where the choice matters at all is narrow: at W=8,192 no rung leaves a single body (the Zone B share is 1,925 heuristic tokens against a smallest root block of 2,587), and at W=200,000 every rung ties at 21 bodies, the whole store.

Settled: width is a reallocation of a fixed Zone B block, not an addition to it. Assembled Zone B is 7,633 heuristic tokens at rung 16 against 7,569 at rung 2 — a 64-token difference in the wide arm's favour, against a Zone B share of 7,701.

Not settled, and now known not to be settleable on this fixture: what width costs at the run level. The arms differ by a median 12,168 input tokens over completed runs (37,513 against 49,681; n=38 per arm, qwen-2.5-72b-instruct through OpenRouter, W=32,768, one epoch; both verified for this report). Iteration 3-C decomposed that gap exactly — the identity B1·T + echo + retrieval + output reproduces usage.input with a maximum residual of 0 across all 76 completed rows — and then showed the decomposition cannot be trusted: a 10,000-resample bootstrap 95% confidence interval crosses zero for every bucket except output length, which is 2.9% of the point-estimate gap and is not a width mechanism. Run-level token standard deviation is 21,269 (tree) and 20,497 (tree-wide), roughly four times the 5,275-token mean gap. Resolving it needs about 246 completed rows per arm, 6.5× today's 38.

Not settled: whether to flip the default. The one measured advantage of the wide arm is a head-stratum mean of 0.333 (3 successes of 9 completed) against 0.091 (1 of 11), both non-tree baselines at 0.000 — and reduced to what happened, all four successes across both arms are on one question, s1-q02-head. On the other three strata both widths are 0.000, and on tail both baselines beat both widths (0.200 and 0.333). Flipping the default is an epoch shift and needs a second scenario, which cannot discriminate at any affordable n until the floor lifts.

3.3 Summary timing — the lag is settled and fixable; the fraction is settled as a target and unmeasured as a value

Settled by definition, not by fitting: the switch point's target is the Zone C fraction of W. The rule defines the switch as the size at which the whole trace fits where the active branch's detail would go, which is Zone C's allocation. The two are now one quantity by construction in deriveZoneBudgets, so the 0.35-against-0.20 drift between the two harnesses cannot recur.

Settled and reproduced twice: the gate lags one turn, and the lag has a measured size. It compares against the previous completed turn's billed prompt, so exactly one prompt above the threshold is always sent. Across the six recorded crossings the overshoot is a median 8,306 tokens, range 126 to 15,564 (n=6, claude-sonnet-5, two scenarios, one epoch). Recomputed for this report directly from eval/results/long-v65-gate/*/results.json without the script: median 8,305.5, identical set. Replayed with the check moved to the prompt about to be sent, median overshoot falls to 0 and worst case to 916, with five of six landing under the threshold, at a cost of 2.7–4.0 milliseconds of local tokenizing against turn latencies recorded in the seconds.

Settled as a refutation: a fraction sweep cannot rank the fractions. From 0.15 to 0.35 of a 200,000-token window over a deterministic 300-branch corpus, the post-switch prompt is a constant 9,060 tokens at every fraction, so total tokens are the raw trace up to the crossing plus a constant afterwards, and an earlier crossing is arithmetically always cheaper. Re-run for this report: the whole table below is identical to what iteration 2 published. The sweep measures its own lower bound. Not settled: which fraction, and whether an early switch buys tokens with turns. Graded score separates nothing here: every cell is 3 of 3 or 5 of 5 at a mean of 1.000, so this dimension is currently unfalsifiable on score and can be ranked only on tokens and turns.

3.4 Caching — the instrument was the problem, and fixing it flipped the verdict

Settled arithmetically from two published rates: a cache write costs 12.5 times a cache read per token, so prefix size is not the lever. The frequency form of that rule — “breaks even below about one turn in twelve” — was a size ratio wearing a frequency's clothes and has been retired in favour of the derivation the frequency question needs: marking a block beats leaving it unmarked while its rewrite frequency stays below f* = (Pinput − Pread) / (Pwrite − Pread), which is 0.7826 at claude-sonnet-5's published rates. That is a formula over three per-model prices, not a constant. Measured against the real trace, Zone B rewrites on 20 of 754 turns (2.65%), far inside the winning side, which is why its single trailing marker is correctly placed.

Settled: the simulator's verdict against the third breakpoint was an artifact of the simulator. ProviderCacheSimulator credited a cache read only when a breakpoint recurred at the same block index as in the immediately previous submission, so a marker advancing one block per turn could never earn a read by construction. Iteration 3-A confirmed the diagnosis at the exact lines, then extended the simulator to track the longest prefix ever confirmed cached and to bill at block rather than whole-segment granularity, reachable as the new default 'automatic-prefix' policy with the original preserved byte-for-byte as 'exact-last-position'.

Settled: with the fixed instrument, the third breakpoint is cheaper, and the shape matches the live run. Re-running eval/scripts/cache-sweep.mjs unchanged for this report reproduces iteration 3-A exactly: session cache reads 6,335,267 tokens for the shipped 2-breakpoint layout against 11,486,477 for the 3rd-breakpoint layout, on an identical 15,130,974-token session total; median per-turn cache-read fraction 0.557 against 0.982; session cost −39.8% (n=754 turns, 1 scenario, deterministic replay, zero model calls). Cache reads climb 7,231 → 19,476 and are non-decreasing on 727 of 753 turn-to-turn steps; writes are delta-sized at a median 113 tokens on the turns that write anything outside a phase transition; fresh input is 0–288 tokens per turn, median 85. The already-published live run of the same design measured cache reads climbing 4,788 → 23,794, writes at about 1.2k median, fresh input 36–892 tokens per turn, and cost per turn down 18% (n=5 replicates, sw-2-multimod). The sign and the shape agree; the magnitude does not, and should not be read as agreeing, because the live comparison bundled several v5.6-era changes on a different scenario while the offline one isolates a single config field.

Not settled: whether to flip cacheZoneCBreakpoint on by default. It remains off. One deterministic single-fixture simulator run is the validation step, not the second-scenario replicate that iteration 2 pre-registered as the gate for a default flip.

5 What was learned, separately from what was decided

The decisions are in §3 and the deaths in §4. What follows is the part that cost the most time and would be invisible in a results table.

5.1 Mechanisms now understood

  • Two counts, one allowance. The fold level and the rendered-body count are paid out of the same Zone B share, so raising one lowers the other. Every earlier statement about “how many summaries the model sees” was ambiguous between them.
  • Depth is emergent, not chosen. A branch closes only when a non-neutral tool call's phase type differs from the open one. The oversized branch spans 207 events because its 64 shell calls and 2 skill calls map to the neutral phase (which extends rather than closes) while every non-neutral call inside it maps to the same type, so the closing condition never fires across 22 alternating runs of tool identity.
  • A branch can never render smaller than its largest atomic event. That is why a segmentation change alone cannot close the over-window boundary, and why a rendering fix was needed alongside it.
  • The switch gate's overshoot is one turn of whatever growth the task is producing — a median 14,784 tokens on these tasks, and 248 tokens on the one crossing that overshot by only 126. The lag adds no fixed cost; it adds a turn.
  • The zone partition is itself a budget, and it manufactured a result. Because zones compete for an invented share of W rather than for W, extra bodies necessarily displace headlines even when the real window has room. The displacement appears and disappears exactly with whether the share binds: 2 bodies against 11 at W=32,768 where the share is 7,701 tokens; every rung tied at 21 at W=200,000 where the share is 47,009 against a whole-store Zone B of at most 16,921; nothing rendered at all at W=8,192 where the share is 1,925 against a 2,587-token root block, though the real window has room for both.
  • A provider's automatic prefix matching cannot be modelled at whole-segment granularity. A moving single breakpoint can only produce a delta-sized write if the simulator can credit part of the segment the marker sits at the end of. Extending which submissions count as history does not fix it on its own.

5.3 An instrument that had to be fixed before it could measure

Iteration 2's fourth experiment was the first thing in the program ever to point the cache assertion harness at the request builder that produced every live caching number. It returned +23% against the third breakpoint. An already-published live run of the same design had measured −18% cost per turn. Both could not be right, and the disagreement was the result: the simulator's read boundary was built from a single previous submission and tested by exact equality of an integer block index, so a marker that advances one block per turn could never earn a read. Iteration 3-A confirmed that at the lines, extended the policy, and the sign flipped. Two lessons generalise. First, a conservative instrument is safe for detecting regressions and unsafe for ranking designs — under-crediting cannot hide a regression, but it can invert a comparison. Second, the validation target was free and already on disk; the cheapest experiment in the pass was the one that checked an instrument against a measurement already paid for.

A live residue of this remains in the tree and the next agent will hit it: eval/scripts/cache-sweep.mjs still prints its pre-iteration-3 conclusion — “the 3rd breakpoint, as coded, sits on the LOSING side of its own crossover” — underneath a table whose own numbers now say the opposite. Verified by re-running it for this report. The narrative line is stale, not the arithmetic.

5.4 A frozen fixture that was being written to, and a metric that was fabricating data

The fixture was frozen only for L0 and L2. eval/fixtures/transplant/s1/store/ is gitignored, so git status proves nothing about it, and the manifest pins trace.jsonl and the config file but not the database. composeRootSummary appends a root-summary version every time a rung is composed that the store has not already seen, the assembler reads the latest version, and that version's text grew from 407 to 1,677 heuristic tokens between one experiment being written and the judge re-running it one minute later. The predicted session delta of 1,270 tokens × 754 turns ≈ 958k matched an observed 1,154,537, of which 1,130,632 was cache read — the right size in the right place. The store today holds 1,546 root-summary versions against 21 branch summaries (verified by SQL for this report). Consequence, and it is retroactive: every published Zone B number in this program is dated by a root version nobody records. The scripts now copy the store to a scratch directory before touching it, which stops new writes; it does not date the old numbers.

A metric was fabricating failures. Two harnesses ran the same kind of bounded tool loop and only one of them had been fixed. In eval/scripts/transplant.mjs, a run that exhausted its six-turn ceiling returned an empty final answer that was fed straight to the grader and scored 0, indistinguishable from a wrong answer — 2 of 60 rows in the primary tree arm and 7 of 60 (11.7%) in the tree-wide ablation, every one of the seven with fetched:true, searched:true, meaning the model was actively using its tools and just needed more than six round trips. The same file already excluded cost_cap rows from scoring for the identical reason, which is what proves it was an oversight rather than a design choice. It is now fixed, and the correction moves a published cell: tree-wide's head-stratum mean is 0.333 over 9 completed runs, not the 0.273 over 11 that earlier reports quote.

5.5 A cause misattributed and later corrected

Three of these are worth carrying, because each was believed long enough to shape a decision.

  • The 16 fabricated failures. A run the harness stopped was graded as a task failure. Corrected twice: first by making harness-stopped runs ungradable, then by narrowing that — a capped run whose hidden tests pass keeps its success, because the grade is a filesystem fact. The narrowed rule recovers 10 legitimate successes and still removes the 16 fabricated failures.
  • Empty replies blamed on the provider. Written off as reasoning models putting text in an unread field; actually the reply clamp being spent on thinking. The root cause was in the harness, not the provider.

The cause is behavioural — 34.8% of sampled rows searched and never fetched, 8.9% never searched — not structural. Nothing about branch granularity or width would move it.

7 Recommended next steps

Ordered by expected information gained per unit of effort, where effort is counted in tokens and runs spent. Items 2, 3 and 5 cost no model tokens at all. Each is specified to be executed cold.

Step 1 — The per-turn reply allowance needs its own round: replay first

Why first. It is the only shipped-library behaviour in this pass that is implemented, unit-tested and never run, and everything offline can show is that the arithmetic is right. What is unknown is behavioural: whether a model given a small allowance produces a usefully short answer or a uselessly truncated one, whether quality degrades gracefully as the allowance shrinks, and where the allowance becomes too small for the task — the floor replyAllowance deliberately refuses to guess.

Substrate. The transplant fixture, not a new long-running scenario. It already is a long session: 754 events, roughly 196,000 tokens, frozen with its hashes. Instead of the twelve isolated question runs it drives today, walk forward through the trace — assemble the prompt as it stood at each point, compute the allowance, and ask a live question at intervals. Every arm then sees byte-identical inputs, so the comparison is same-epoch by construction. This needs one harness change: transplant.mjs asks its questions at a single fixed store state today, so an interval-walk mode has to be added before any run.

Arms (one variable, three levels): no-limit — send no max_tokens, today's live default; fixed-ceiling — the removed behaviour and the control the existing corpus was measured under (8,192 in the live harness, 800 in the portability one; use 800, because that is the clamp the fixture's own numbers were produced with); allowance — BudgetReport.replyAllowance passed straight through as max_tokens.

Flags. EVAL_LAZY_TOKENS derived from the window rather than set to 30,000, so the switch is the Zone C share as the rule requires; the seven gate flags on; cacheZoneCBreakpoint off; neutralPhases: ['other']; ladder tree. No --max-turns, no --time-cap-ms; bound spend with --cost-cap-usd and let stall detection end a run that will not finish.

Model and window. openai/gpt-3.5-turbo at W=16,384, through OpenRouter. Not a preference: the mechanism only engages once the prompt approaches the window, and this is the smallest window in the fixture and the only cell where the tree arm completed 60 of 60 runs. Run the same design at W=32,768 on qwen/qwen-2.5-72b-instruct only if the small-window cell shows a curve worth confirming.

n. 12 questions × 3 arms × 5 replicates = 180 attempted runs at W=16,384, all interleaved in one epoch.

Pre-registered win criterion. (i) Primary: the allowance arm's mean graded score is at or above fixed-ceiling's at every allowance decile, with the baseline on disk being the tree arm's existing W=16,384 cell. (ii) Primary: the allowance arm completes at least as many runs as fixed-ceiling — the claim is that a session continues where a fixed ceiling would have made the request invalid. (iii) Guard: median run tokens for allowance no worse than fixed-ceiling's baseline of 13,107 (n=60 completed, verified for this report). (iv) Guard: the fraction of replies stopping at the allowance rather than at the model's own stopping point is recorded per arm; it is a diagnostic, not a criterion.

Pre-registered refutation, carried verbatim from the queue. The failure that would refute the change is a run where shrinking allowances produce truncated-but-scored answers, because that trades a loud failure for a silent one — the opposite of what the change is for. Operationally: if the allowance arm's share of replies ending at stopReason: 'length' rises while its graded score holds or falls, the mechanism is hiding truncation and must be retired.

What the replay cannot show, and it matters. A frozen replay breaks the feedback loop. The allowance changes what the model says, what it says changes the trace, and the trace changes the next prompt. The replay settles answer quality at each allowance level and the shape of the curve; it cannot show whether shrinking allowances change the session's trajectory. A genuinely long live run is the confirmation, worth paying for only after the replay says there is something to confirm, and scoped to whichever allowance regime the replay says is interesting. Do not run them in the other order.

Estimated tokens. 180 runs × a median 13,107 tokens per completed run at this cell ≈ 2.4M tokens, essentially all of it fresh input, since this endpoint bills no cache.

Why last. Every limitation in every dimension is the same limitation — n=1 store, one trace, one host's tool-name map. The offline recipe is already written and runs at zero model tokens: re-segment a second store's event log under both configurations, locate each question's sequence in the new segmentation, count branches and sizes, and re-run the harness's own zero-token structural gates against each candidate's re-derived tree. That last part is the missing step even on s1: a candidate that multiplies branch count by 4.71 changes how many branch summaries fit a given allowance, which is exactly what the over-budget gate asserts, and its interaction with the fold level is unexamined.

The width-cost replicate is dominated and should not be bought yet. Resolving the 5,275-token mean gap needs about 246 completed rows per arm, roughly 390 attempted per arm at the fixture's 63% completion rate, about 780 runs and 29M tokens at the W=32,768 cell's median — and step 6 may change the arms' behaviour enough to invalidate the whole batch. Buy it only after step 6 lands and only if the floor lifted.

8 Standing constraints the next agent must respect

  1. No budgets or caps. Not on turns, not on wall-clock, not on reply length. Bound the resource itself: spend by a spend cap, a run that will not finish by non-progress. Two of these have already corrupted measurements here — a turn ceiling fabricated 16 failures and a reply clamp produced empty answers that were then graded wrong.
  2. Never delete a rule to satisfy a constraint that is itself a guess. Reply headroom is required by the algorithm, because prompt plus reply must fit the window; a reply ceiling is not. The distinction is explicit in the code and must stay explicit in any change.
  3. Do not silently deviate from a D-numbered decision. If implementation shows one is wrong, say so, propose the change, and update the decision row.
  4. L1, L3 and L4 are derived. Never write a migration for them. Changing the segmenter or a summary prompt means deleting the derived layers and rebuilding. Summaries are versioned, never overwritten.
  5. Prompt layout is fixed; only content migrates. Zone A, then Zone B in creation order, then Zone C. Zone B is never relevance-ordered — reordering a cached prefix is the cache killer. Retrieved results append after Zone C.
  6. Ingestion is hermetic. It reads the event log, the payload store and a parser, and calls nothing over a network.
  7. An epoch shift forfeits every comparison across it. Re-segmenting, flipping the ladder default, and moving the switch check all change what gets built or when. Declare the boundary at the commit and never compare a total-token, turn-count or cost figure across it.
  8. Never grade a run the harness stopped as a task failure. A failing grade becomes success: null. The one exception is narrow and deliberate: a capped run whose hidden tests pass keeps its success, because the grade is a filesystem fact. A stall keeps both directions, because ending in a loop is a real task failure.
  9. Report metrics as tokens, turns, graded score and success counts; means for scores, medians for tokens and turns; state n everywhere. Dollar figures appear once, in a footnote, beside the baseline they are relative to — never as a bare figure in a claim.
  10. Every comparison pairs candidate against baseline at the same model and the same epoch. Where a same-epoch baseline does not exist, say so in the same breath as the number; three of the six recorded cache-invalidation mechanisms have no valid baseline and are reported as within-run or before-and-after observations only.
  11. Price a segmentation or rendering proposal with a real tokenizer, never with the corpus-wide ratio. The ratio undercounted two branches by 43% and 67%.
  12. Copy the frozen fixture before touching it, and check git status after. Its store directory is gitignored, so git status alone proves nothing; the copy is what protects it.
  13. Unknown tool maps to other, never a crash. The tool-to-phase map is the one row every port must edit.
  14. A conservative instrument can invert a comparison. Under-crediting cannot hide a regression but can flip a sign, so validate an instrument against a paid-for measurement before letting it rank designs.
  15. No total-token figure in this program includes leaf-summarizer cost. The harness's total counts the agent model only. Quote totals with that caveat until step 5 lands.
  16. Do not run a live width or depth arm before the retrieval floor lifts. With 9 of 12 questions at exactly zero across both widths and every rank, no affordable n discriminates.

9 What this pass did not test

Stated as scope, so a next agent does not read an untested condition as a settled one.

  • Live model calls: none. No experiment in any of the three iterations called a model. Every live number here was already on disk when the pass started, from batches run on 1–2 September.
  • Stores: one. Every structural number — the 77-fold branch spread, the 21-versus-99 re-segmentation, the ladder curve, all four cells of Table 1, the cache replay, the width decomposition — comes from transplant/s1: one trace, one task, one host's tool-name map, 754 events. Whether the neutral-merge mechanism or the size spread is a property of the rule or of this one session is the single largest unknown.
  • Windows: assembled at five, scored at two. Structural gates run at 8,192 / 16,384 / 32,768 / 65,536 / 200,000, but no scored run has ever been made at 8,192 (a dead cell for both tree arms), at 65,536, or at 200,000. The 8,192 cell is the clearest evidence for deleting the zone partition and has never carried a model call.
  • Models: four, and not interchangeably. Width and depth numbers are qwen/qwen-2.5-72b-instruct and openai/gpt-3.5-turbo through OpenRouter, which bills no cache at all — every rewrite claim in this pass is Anthropic-specific, and the OpenRouter path reports cacheWrite: 0 by design. Timing and caching numbers are claude-sonnet-5 with claude-haiku-4-5 summaries. No dimension has been measured on more than one model family.
  • Caching × width: not measured. The width dimension was measured entirely on an endpoint that bills no cache. Under a cache the same reallocation is nearly free while the prefix is stable and expensive at each rewrite, so a width policy chosen there may be the wrong one here. That coupling is between dimensions 1 and 3 and nothing has measured it.
  • Providers: one, for every cache claim. No non-Anthropic provider in this repository reports a cache-write count, so nothing at all has measured a breakpoint scheme on a second provider.
  • Summary quality at either granularity: not measured. The candidate segmentation puts many branches at roughly one tool call plus its result, and 47 of its 99 branches carry no phase identity beyond other. Whether a summary of that little work is worth its own leaf pass is untouched.
  • Turns and score under the candidate segmentation: unmeasured on every task, short or long. Only containment and branch count have been measured, so the question the fourth rule asks — which setting wins — is open.
  • The reply allowance live: never run. That is step 1, and its trajectory question cannot be answered by the replay that step 1 buys.
  • The listing-then-range fetch path: exists, untested live. It is the only lever left on the three branches over W=16,384.
  • Contract v2 and v3: registered, unreachable. The shipped server always installs v1 and has no configuration field to choose otherwise, so the tier-2 table's “host, if a smaller model needs different instruction” overstates what is configurable.
  • Populations the scenarios never exercised. Twelve questions in four strata from one frozen trace — not a live session whose composition could be observed. Every graded scenario in the timing dimension scores 1.000 with every replicate passing, so no timing policy can currently be shown to make an agent more reliable, only cheaper or dearer. And no scenario in the program separates the arms on reliability at all once harness-stopped rows are excluded.
  • A multi-entry or TTL-bounded cache: not modelled. The simulator's automatic-prefix policy tracks one running prefix. A real cache holding several entries under a time-to-live could do better than these numbers, never worse.
