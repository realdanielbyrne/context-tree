Loop 9 checkpoint: an instrument, a corrected gate, and a corrected number

Context-tree evaluation program, loop 9 (checkpoint) · September 2, 2026 · code at commit a6f85ca

Status. This is the checkpoint report for loop 9. Items 1 and 3 are complete and final. Item 2's design pass, instrument-hardening and offline gates are complete; its live scoring batch was launched after this report was written, so §5 carries one explicitly marked placeholder and nothing else in the document depends on that batch's outcome. Loop 8's interim report [1] introduced the evaluation method, the transcript baseline, the six software tasks and the v6.x configuration this loop starts from; the supplementary note [2] introduced the per-turn context charts. The algorithm as it currently runs — twelve lines of pseudo-code, a simplicity audit and a configuration-parameter register — is stated in one place, reports/algorithm.md [3], and reproduced verbatim in Appendix A.

Abstract

Context-tree reorganizes an agent's linear conversation into a summary-headed tree so that the prompt carries a short summary per completed phase of work instead of the raw history, with tools to fetch any detail back on demand. Loop 9 ran three items and stopped. Item 1 replaced the switch that decides when to start summarizing — it estimated trace size as characters divided by four and never fired — with the provider's own token count of the previous turn, and made the crossing one-way after an unlatched version oscillated across the threshold twice in one run; the gate now fires on 6 of 6 live runs and per-turn growth behind it falls from 2,046–4,928 to 256–915 tokens per turn, below the transcript baseline's own 812–2,094, but final-turn context stays 1.13–1.27× the baseline and total tokens rise 48–77%, because a 30,000-token absolute switch forces a transition a 200,000-token model does not need. Item 3 re-measured the published 3.4× token gap on sw-3-refactor within one epoch at n=5 and found 1.71× with equal median turns; both candidate deletions measured null, and the batching-density mechanism was refuted (p = 0.81). Item 2 built a cross-model transplant instrument — one frozen 754-event trace, 15 offline gates, five hardening rounds — and its recorded runs attribute the tree's zero on late-trace questions to a tool-use policy, not a resource limit: no fetch was ever truncated, and 53.6% of failures never issued a targeted fetch at all. The main limitation is that no arm of that instrument has yet been scored under the corrected design.

1 What loop 9 set out to do

Loop 8 closed with six recommendations [1, §5]. Loop 9's scope, set by the owner, took three of them and stopped: item 1, measure the summarization threshold with real tokens instead of a character estimate; item 2, build the cross-model transplant test, which asks whether a tree built from a large model's conversation lets a small-window model answer questions about that conversation; item 3, close the short-task token gap on sw-3-refactor. Then checkpoint. This report is that checkpoint.

Some terms first, each used throughout. An arm is one way of building the prompt, held against the same task and the same model. The native transcript baseline (native in the live harness) is the default behaviour of agent harnesses: the prompt holds the whole conversation, re-sent every turn. Context-tree is the candidate. A branch (a phase in the prose of earlier reports) is context-tree's unit of organization — a contiguous stretch of work on one sub-problem, which receives a short summary once it closes. The prompt has three fixed sections, called Zone A (the frozen system contract plus the tool schemas), Zone B (the root summary and the branch summaries, always in creation order) and Zone C (the active branch's raw detail); tool results append after Zone C so the cached prefix is never disturbed. Storage is layered: L0 is the append-only event log, L1 the SQLite tree of nodes and versioned summaries, L2 the content-addressed blob store, L3 the vector index. A turn is one model call. Context size per turn is what the model saw on that call — fresh input plus cache reads plus cache writes, as the provider reports them.

Two measurement conventions hold everywhere below, and they are the reason several published numbers move in this report. Effort is reported as medians of tokens and turns; accuracy is reported as the mean of a 0/1 graded score, alongside the raw success count. And a comparison is only made within one epoch — one batch, one day, arms interleaved — because the alternative produced a headline that was wrong by a factor of two (§4).

2 The transplant test as an instrument

2.1 What it measures

The transplant test takes one real, finished conversation from a large model, freezes it, reorganizes it once into a tree, and then hands that tree to a different, much smaller model together with a question whose answer lies somewhere in the original conversation. It is the only experiment in the program that separates the organization of context from the model that produced it. Nothing is re-ingested or re-summarized after the freeze, for any arm, at any window.

The substrate is one Claude Code transcript of 4,663,077 bytes (sha256 e1b289c3…), imported to 754 L0 events, 46 L1 nodes (one task, 21 branches, 24 file nodes), 22 summaries and 697 L2 blobs. Counted with a real byte-pair tokenizer rather than a character estimate, the whole transcript is 196,385 tokens — 11.99 times a 16,384-token window and 5.99 times a 32,768-token one. That is the precondition of the whole test: the answers provably lie outside both windows.

Five arms were scored or run. naive-full sends the whole transcript and is a precondition, not a result: it is expected to fail, and it did, on all 12 attempts per model — the qwen provider replied 400 … maximum context length is 32768 tokens. However, you requested about 171471 tokens. truncate-tail keeps the newest messages that fit and summarizes nothing. compact-rolling is the honest competitor, and the only arm anywhere in this program pinned to the candidate on three axes at once — same summarizing model, same 1,024-token output cap, same total prompt budget; it is what production harnesses actually do. tree is context-tree. tree-wide is context-tree with the root-keep ladder walked from the smallest rung up, trading a smaller root block for more visible branch summaries.

Questions are stratified by where the answer sits. head means early in the trace, tail means late, deep means the answer literal appears in no stored summary and so forces a search-then-fetch hop into raw L0, and spanning means it crosses branches. Three questions per stratum. Each answer is a literal string that occurs exactly once in L0; grading is an exact regex match with no model call, so the grader and the question-writer are never the same mechanism.

Budgets are derived from the target window rather than hand-tuned. The fractions are response .05, Zone A .10, Zone B .20, Zone C .20, lazy .35, slack .10, each divided by the measured heuristic-to-BPE ratio of 0.850897 (itself measured as 207,395 ÷ 243,737 tokens over all 697 blobs). At W = 32,768 that gives Zone B 7,701 tokens and Zone C 7,701; at W = 16,384, 3,850 each. Fifteen offline gates (g1–g15) must pass before any answering token is bought: trace hash, hermetic import, meta-line skipping, an empty unmapped-tool list, L1 rebuild determinism, the native-exceeds-window precondition, the BPE ratio, an empty over-budget list at every window, Zone B nesting across windows, prefix stability across assemblies, literal uniqueness, the leakage gate, the manifest hash, the cost-cap plumbing, and self-retrieval.

2.2 The five hardening rounds

The instrument did not work on the first attempt, or the second. Five defects were found and fixed, each of which would have produced a publishable-looking number that meant nothing. They are the methods contribution of this loop, and they are listed here because each one is a trap any similar experiment can fall into.

Empty questions. The first frozen question set carried a source literal and a stratum for all twelve rows and an empty question string for all twelve. Nothing downstream noticed: the arms assembled, the model answered, the grader scored. The fix is a floor and a gate — a question must be at least 20 characters and 4 words (questionTextValid), and g12 now asserts all twelve are non-trivial before any batch runs.

Underdetermined referents. A literal can be unique as a string in the log and still not identify anything. "How many characters were omitted from the excerpt when it was truncated for length?" has the string-unique answer 2650 and hundreds of equally valid referents in a trace full of truncations; qwen found a different truncation, reasoned correctly about it, and scored zero. Two changes followed. The paraphraser's context window was widened from 200 to 750 characters, because a 200-character window gives it no neighbouring detail to name; and a new gate, g15, asks the harness's own context_search to find a question's source from the question text alone, so that a question whose source is unreachable by retrieval is rejected by construction rather than scored as a model failure. A second half of g11 was added for the same reason: one literal, one question. Without it, s1-q01-head and s1-q07-deep were asking about the same file path, because deep is drawn from a subset of head.

A provider bug that ate 23% of the first scored batch. fromOpenRouterResponse indexed response.choices[0] directly. An error body has no choices key at all, so indexing it threw before the guard below could name the real problem, and the run was recorded as an infrastructure failure of unknown cause. The one-character fix is response.choices?.[0]. It cost 14 of 60 runs in the first scored transplant batch. The residue is still visible in the recorded data: 21 of 135 sampled rows (15.6%) are provider failures, and one cell — tree on the spanning stratum at qwen/32k — lost 10 of its 15 replicates, which is why no conclusion is drawn from spanning anywhere in this report.

A self-retrieval gate that could not fail. g15 was written with SELF_RETRIEVAL_TOP_K = 20, and the lexical beam returns 19 candidates. A threshold at or above the size of the returned list accepts every result the search can produce and proves nothing. The gate reports its own vacuity — gates.json carries "vacuous": true and the detail string says so in words — which is the only reason it was caught. The replacement, not yet in force, is a strict top-5 threshold; the diagnostic value already extracted from it is the per-question rank table of §2.4.

Question paraphrase, and one discarded artifact. Questions are written by a third model family that sees only the raw L0 span and never the node id, the branch id, or which tool would surface it, and they are rejected if they share a 3-gram with the source branch's stored summary after the answer literal itself is removed from the comparison — the carve-out matters, because a question that must contain its own answer token would otherwise always be rejected. Two attempts per literal, then the literal is discarded rather than the question weakened. In the same spirit, the first W = 16,384 compaction artifact was thrown away and rebuilt: its rolling summary had collapsed to a 169-character conversational fragment, because the build loop accepted the model's raw reply as the running summary and every later chunk compounded it. Scoring against that artifact would have handed the tree a free win. The discarded build is recorded as spent-and-discarded, not quietly absorbed.

Four things in these runs can be attributed to a mechanism, and are the reason the design pass of §5 exists.

The model searched and then stopped. Classifying all 135 sampled rows, 47 (34.8% of rows, 42.7% of the 110 non-infrastructure failures) issued a context_search and never followed it with a context_fetch; a further 12 never called a tool at all. Together that is 43.7% of rows and 53.6% of failures. It is worst exactly where the prompt already shows something plausible: 52% of tail failures searched and stopped, against 41% on head and 19% on deep. The structural explanation is clean. At W = 32,768 the root-keep ladder picks a keep of 16, leaving room for two branch summaries covering L0 sequence 639–754; all three tail sources sit inside that range and all three head sources sit outside it. On tail, a compressed one-paragraph summary of the right branch is already in the prompt, unrequested, and a model that trusts what it can see has no reason to reach for a tool — while the baselines hold the same range as raw, uncompressed text.

No fetch was ever truncated. In the entire 110-row failure sample there is not one case of a correctly-targeted context_fetch being cut off — zero. Six rows fetched the right branch, suffered no truncation, and still scored zero. This matters because it removes the most obvious resource explanation: the tool was not running out of room to answer with.

The harness never logged how deep the model fetched. context_fetch takes an optional depth argument that defaults to a summary, and an optional file argument, and the harness recorded neither — only the query text and the branch id. So for those six rows it is not mechanically decidable whether the tool handed back a paraphrase that could not contain the literal, or handed back the verbatim text and the model failed to extract it. That ambiguity is precisely what separates a surface defect from a competence limit, and the recorded dataset cannot settle it. Logging call.input verbatim is the single highest-leverage free fix in the instrument, and it is the first step of the design in flight.

The search payload overflowed the small window. A context_search result carries each hit's entire untruncated summary text, plus a duplicate 240-character snippet list. Serialized over this store at the configured limit of 20 hits, that is 45,470 characters — 9,673 tokens — for one tool call. At W = 16,384 the measured headroom for appending a tool result is about 10,251 tokens on turn 1, a mean of 5,392 on turn 2 with a floor of 86, and essentially nothing by turn 3. Eight of 15 sampled gpt-3.5 rows show the search result itself truncated by 2,700 to 16,000 characters. This never happened once at W = 32,768, where turn-1 headroom is about 22,825 tokens. Whether the correct hit was among the characters dropped could not be determined, because the raw hit list was not logged either.

2.4 What the analysis found in the code

Four further findings come from reading the shipped code against the plan rather than from the runs, and each one changes what the next batch should test.

The retrieval providers are dead wiring. The plan specifies five retrieval providers — structural, fuzzy, and grep — merged in a fixed order, and all five exist as real implementations, 1,123 lines of them. Nothing anywhere constructs the registry that would make them reachable: not the MCP server, not the CLI, not the evaluation harness. The search tool degrades gracefully to the tree-only path, so nothing crashes and nothing announced itself. The server also wires no embedding model, so the vector path never runs either. Every search measured in this program, in every loop, has been a lexical beam over generated summary prose. That is a plan gap, not a design gap, but it means the retrieval claims are narrower than they read.

Drill-down already exists, through node ids. The mechanism of "fetch a summary, then zoom in on the sub-part you want" is already in the code: a summary-depth fetch returns the node's own id and its direct children's ids, uncapped, and context_fetch accepts any node id rather than only a top-level branch. On this store the tree is two levels deep, so one call already hands back every child id and a second call gets that child's raw content. What does not exist is a way to get the child list without paying for the summary body, a way to keep discovering descendants after going to full depth, a way to scope a search to one subtree, or a way to read a middle slice of a large span rather than always its prefix.

Drilling to a leaf does not always reduce anything. Eleven of the 21 branches have no file children at all, and in every parented branch inspected, the first child's span is byte-identical to the parent's — the "leaf" is the same bytes. Where the leaves do differ, the sizes are the constraint. The median file leaf is 17,998 characters (about 4,500 tokens), the ninetieth-percentile leaf 60,886 (about 15,222) and the largest 99,823 (about 24,956), against a combined lazy-plus-slack allowance of roughly 10,600 tokens at W = 16,384 and 17,300 at W = 32,768. So a median leaf is comfortably affordable at either window; the ninetieth-percentile leaf exceeds the entire allowance at 16,384 and consumes 88% of it at 32,768; the largest exceeds it at both. The only sub-branch unit that actually reduces anything on this fixture is a sequence range.

Summaries cannot rank what they do not contain. The lexical beam ranks a question's own source at a median of 10.5 out of the 19 candidates it reaches, with 2 of 12 sources in the strict top 3 — near the middle of an effectively unordered list. An embedding client was built and the store's summaries were embedded, at a total spend of two hundredths of a cent, to see whether meaning-based ranking moves it. Table 2 is the result: the median rank is 10.5 either way. The vector path does rank over a larger candidate pool (21 rather than 19, because the beam prunes and the flat nearest-neighbour search does not), and it lifts strict top-5 from 3 of 12 to 4 of 12, which is exactly the threshold that licenses a live semantic arm — a pass at the minimum margin, not a comfortable one. The reason the movement is small is structural rather than a defect in the embedder: none of the twelve answer literals occurs anywhere in any summary, in any version, over 1,339 summary rows and 45,057 characters of current summary text plus metadata. A better ranking over summaries cannot surface a literal the summaries do not contain, and by construction the whole deep stratum is defined by that absence.

3 Item 1 — the real-token gate

Below a size threshold, context-tree runs in devolved mode: it shows the whole trace and summarizes nothing, on the argument that summarizing a short conversation costs money for nothing. The switch out of devolved mode is the lazy gate. Until this loop the gate compared traceChars / 4 against a 30,000-token budget, and on code-dense traces four characters per token undercounts badly. Measured on the six loop-8 tree runs, the trace the tree was showing at the final turn was 33,951 to 39,404 tokens as the provider billed it — 13% to 31% above the budget — while the character estimate reported it as still under, for the whole run. The gate never fired once. That is undercounting, not a threshold set too high, and it is why every live tree run to date tracked the baseline's growth curve instead of flattening.

The replacement is the provider's own count of the prompt it last billed — input plus cache reads plus cache writes from the previous completed turn — which every turn already returns at no extra cost, is exact for whatever model is running, and needs no tokenizer kept in step. The change is four lines.

3.1 The oscillation, and the latch

The first live replicate with the real-token gate crossed on its ninth model call with a 40,158-token prompt, summarized, and on the next call read a prompt below 30,000 — because Zone C then held only the active branch rather than the whole trace. The gate read that as "the trace fits", re-expanded everything, and crossed a second time two calls later at 43,331 tokens. That run finished in 12 turns and 223,917 tokens, about twice the loop-8 tree's cost on the same task. The batch was discarded.

The condition is ill-posed rather than merely noisy. It asks whether the whole trace fits the budget; after the crossing the prompt no longer contains the whole trace, so the prompt's size is no longer evidence either way, while the trace itself only grows and can never fit again. The crossing is therefore one-way and the flag that records it latches. This is a proof, not a heuristic — L0 is append-only — which is why it is allowed to be a condition in a twelve-line algorithm. A character count could never have exposed it, because a character count only increases.

The published criterion had two halves [2, §5 item 1]: the curve flattens at the crossing instead of tracking the trace, and final-turn context falls below the baseline's on at least one scenario. The first half holds cleanly. The gate fired on all six runs, exactly once each, and behind every crossing the growth rate falls from 2,046–4,928 tokens per turn to 256–915 — slower than the transcript it competes with. That is the behaviour the offline 200-branch simulation predicts and no live run had previously shown. The second half fails on both scenarios. Final-turn context is 24,299 and 22,837 tokens, which is 35% and 39% below the loop-8 tree's 37,585 and 37,615 — a large move in the right direction — but still 1.27 and 1.13 times the baseline's 19,157 and 20,191.

Total tokens rise rather than fall: 48% above the baseline on sw-5-dozen and 77% on sw-6-ripple, 35% and 22% above the loop-8 tree. Two mechanisms account for it. The gate reads the previous completed turn, so it detects the crossing one call late, and one batched turn on these tasks is expensive — five of six crossings landed 6,657 to 15,564 tokens above the budget, and those overshoots are billed at cache-write rates because the whole prefix is rewritten when the tree reorganizes. And the transition costs turns: the median goes from 9 to 13 on sw-5-dozen and 12 to 18 on sw-6-ripple.

3.3 The criterion was the finding

The largest prompt any of these eighteen runs assembled is 45,564 tokens. The model has a 200,000-token window, so there were 154,436 tokens of headroom at the worst moment of the worst run. Nothing was in danger of overflowing anything, and a switch derived from the window rather than fixed at a constant would not have crossed at all — the transplant harness derives its lazy budget as 0.35 of the window, roughly 70,000 tokens on a 200,000-token model before the ratio correction, and under that rule the tree would have stayed devolved from the first turn to the last of both tasks. On this evidence that is the right answer.

So the published criterion asked the harness to force a transition the model did not need, and then measured what forcing it costs. What was learned is the cost of the transition, not the value of the tree. The gate itself is now correct: it fires once, on a number the provider supplies rather than a guess, and the growth behind it is slower than the baseline's. The remaining question is not how to make the switch cheaper but where the switch belongs, and that is the single-derivation candidate. Two harnesses currently answer "when should the tree stop showing the raw trace?" two different ways — the live loop reads an absolute EVAL_LAZY_TOKENS = 30,000, which is 15% of a 200,000-token window and fires on traces that were never at risk; the transplant harness derives 0.35 of the window, which on these traces never fires. Neither number is argued for. The quantity the switch actually protects is Zone C, the zone that holds the active branch in full, so the switch belongs at the Zone C fraction (currently 0.2) of the same window-derived budget, in one derivation both harnesses import. The fractions themselves are the decision recorded as D19: response .05, Zone A .10, Zone B .20, Zone C .20, lazy .35, slack .10, each divided by the measured heuristic-to-BPE ratio. Until that lands, no comparison of the two arms is measuring the policy we would ship.

The 3.4× was mostly a cross-day artifact. Measured in one epoch the tree runs 1.71× the baseline on tokens, with the same median turns and a tighter turn distribution — the tree's turn variance is 1.3 against the baseline's 9.8. The 1.5× bar published in loop 8 is still not met; the remaining gap is 28,594 tokens at the median. But the number that had been driving the roadmap was wrong by roughly a factor of two, and it was wrong for one reason: two arms compared across different days.

The batching-density mechanism is refuted. The leading explanation for the gap had been that the tree issues its tool calls in smaller batches and therefore takes more turns, each of which re-reads the whole prefix. Measured same-epoch, tool calls per tool-using turn are 2.15–3.38 for the baseline and 2.25–3.20 for the tree, an exact two-sided Mann–Whitney p of 0.81 on five pairs against five. The earlier "2.77 against 1.49" came from three fast baseline runs on a different day. With no separation at this sample size the pre-registered rule says stop spending on batching, and the residual is per-turn prefix size: Zone A carries 1,582 more tokens per turn under the tree than under the baseline.

Both candidates are null. Arm C deletes one section of the system contract, 246 of its 791 tokens — a real and free saving of about 246 tokens per turn. Arm D removes the completion gate, the rule that nudges the model once when it stops calling tools without confirming it is finished. Paired against arm B replicate by replicate, removing the gate changed turns by +2, +3, −2, +3, −1 where the pre-registered prediction was exactly −1 on every pair, and changed tokens by +16.8k, +48.6k, −41.0k, +21.0k, −12.3k. The trimmed contract changed turns by 0, +2, +3, −2, +6 — and a turn-count change in either direction was named in advance as the falsifier for "the deleted prose does no behavioural work." 6 What the algorithm looks like now

The algorithm as it currently runs is stated in one document, reports/algorithm.md [3], which is the reference description: twelve lines of pseudo-code, a table saying where each line lives in the code and what established it, a simplicity audit, a configuration-parameter register, a line-budget ledger, and the candidates that have a judge verdict but are not yet in force. Implementers change the code and that page in the same change. Appendix A reproduces the twelve lines verbatim.

The budget was set to twelve lines before loop 1 and the count is at the limit. Loop 9 spent no new line: item 1 replaced the characters÷4 comparison inside line 3 and added the latch as line 4, absorbed by merging the old statement about Zone C and Zone B into line 3. The standing constraint is that rule-removal beats rule-addition, and that a candidate replacing a rule outranks one adding a trigger. Any candidate from the loop-9 design panels that adds a line must name the line it replaces.

The audit of conditions produced one deletion candidate, and it is worth stating because it is the shape of finding this rule is meant to produce. Line 7 chooses what fills Zone C with a three-way fallback: the open phase, else the latest branch, else the root. But the segmenter closes every phase on re-ingest, so the function that finds an open phase always returns nothing in the live harness and the first branch of that chain has never fired. It is a condition carried for no observed case.

7 Limitations, and what this loop did not test

The instrument has not yet scored the design it was hardened for. Every transplant number in §2.3 comes from an epoch that predates the per-call logging fix, the search-payload change and the contract variant, and by the epoch rule those rows can never be pooled with the coming batch. The scored cells are therefore a starting point, not a result about the corrected design.

One fixture. Every structural claim in §2.4 — that file leaves are byte-identical to their parents, that the only sub-branch unit that reduces anything is a sequence range, the leaf-size distribution — is measured on one store. Whether any of it generalizes is untested; two further scenarios are identified but not built.

The failure this loop's design cannot fix. All three tail sources sit inside the range the prompt renders inline, and half of tail failures searched and then stopped. Every change in flight lives behind a tool call and is unreachable by a model that never makes one. If both winning arms reproduce a tail score of zero with no fetch on most replicates, the right reading is neither that the surface is inadequate nor that the policy is, but that the prompt is too convincing — the branch summary reads like an answer, and the grader then scores it zero because no summary contains any literal. The remedies for that are content changes not attempted here: a summarizer that carries verbatim identifiers into the summary's own metadata, or a Zone B render that marks summarized branches as non-quotable.

Query formation. The question with the best self-retrieval rank in the whole suite — rank 1 of 19 — was never once fetched correctly, in fifteen replicates, because the model queried for a test file when the answer was an import line. Nothing in this loop makes a model ask about a thing it has no reason to suspect exists, and semantic search reorders a candidate list rather than forming the query.

Item 1's remaining asymmetry. Its baseline rows were collected the day before its candidate rows. That is same-code-path — the native arm has no lazy gate to regress — but it is not same-epoch, and it is the very asymmetry that item 3 proved can cost a factor of two. The n = 3 result should be read with that discount until the single-derivation change forces a rerun anyway.

Small samples, stated. Item 1 is n = 3 per scenario. Item 3 is n = 5 per arm, and its own conclusion is that a live batch cannot resolve a two-to-three-thousand-token effect at any affordable size. The transplant cells are n = 15 attempts per arm and stratum, of which up to 5 were lost to provider failures.

Not touched at all. The public benchmark matrix (adapters exist for four suites; only the internal software tasks have data). Real session resumption. Provider-side cache-prefix survival under a widened Zone A — the gates measure Zone A's size, not whether a provider's cache actually holds across the change. The spanning stratum. And the whole provider fan-out described in the plan, which remains unconstructed.

8 Open items and recommendations

Ordered by expected information gained per unit of effort, where effort is counted in tokens and runs. The first three cost no runs at all and two of them are the direct lessons of this loop; the last two are the largest purchases on the list.

  1. Derive the lazy budget once, from the window, and share the derivation between both harnesses. Zero runs, zero live tokens: delete the live harness's absolute 30,000-token switch, derive it from the window as the transplant already does, and put the switch at the Zone C fraction — the zone it actually protects — so line 9 of the algorithm becomes true of both harnesses. Until this lands, no arm comparison is measuring the policy we would ship, which makes it a precondition for almost everything below rather than a task among them. Verified offline by re-running the existing budget assertions at several window sizes.
  2. Adopt the no-cross-epoch-headline rule. Zero cost, and it is the highest-value thing loop 9 learned. A comparison enters a headline only if its arms ran in one batch, interleaved, on one day. The published 3.4× gap that shaped two loops of roadmap was 1.71× when measured this way. Where a same-epoch rerun is not affordable, the cross-day figure may appear in the body, labelled, and never in an abstract or a recommendation.
  3. Adopt the model pre-screen rule. One tool-use probe call per model before it enters a scored grid, and route a model that cannot emit parseable tool arguments to a no-tools variant with the affected strata reported as untestable rather than as zeros. This costs three calls and it is the cheapest available insurance against the failure that cost 14 of 60 runs in the first scored transplant batch and still leaves 15.6% of the recorded sample unusable.
  4. Promote the v6.5 candidate configuration to core defaults — the decision this report gates. Seven environment flags currently sit in front of what is, on the evidence of loops 7 through 9, simply the algorithm: deterministic root composition, no schema text in Zone A, fetch-as-events, the cache flags, and a 40-headline root keep, plus item 1's real-token gate and its latch. Every one has a measured justification and none has a measured cost. Promoting them buys no new information, but it removes an entire class of configuration error from every future run, and it retires three dead flags in the same change. It is gated on this report because the evidence for the last of them is item 1 (§3), and that evidence is now in.
  5. Land item 2's batch and read it against Table 8. Already designed, gated and budgeted: 276 committed runs across five arms and two cells, arms interleaved within each cell. The instrument work that makes it worth running — verbatim per-call logging, and the boolean recording whether the answer literal ever reached the model in a tool result — is what converts a null into an attribution, which is why this ranks above the benchmark matrix despite costing a comparable number of runs.
  6. Populate the public-benchmark matrix. The largest purchase and the largest external value. Adapters exist for four public suites and only the internal software tasks have data; loading them, then producing the cross-model table at fixed models and window sizes, is what turns this program's claims into something a reader can check against a benchmark they already trust. It is last because every run it buys is spent on generality rather than on resolving a mechanism, and three of the mechanisms above are still open.
