Reading a cached prefix against rewriting it

Context-tree evaluation program · tuning dimension 4 of 4, how caching is handled · September 2, 2026

Status. This is the full treatment of the caching dimension summarised in reports/algorithm.md. It reports no new live runs. Every number is read from committed source, recomputed here from committed run files, or derived arithmetically from two published rate constants; the section that says which is which is §8. Two of the source plan's figures did not reproduce and one of its file citations was wrong; those corrections are stated where the numbers appear, and the reproduced values are the ones used.

Abstract

A provider prompt cache stores the leading bytes of a request and charges a reduced rate when a later request repeats them. Two rates govern it: writing content into the cache, and reading it back. On the model this program runs, a cache write costs 12.5 times a cache read per token. That single ratio settles the dimension's central question without a model call: a stable prefix that is read on every turn is cheaper than the same content rewritten on every turn by exactly that factor, and prefix size is not what decides it — a re-read prefix can be 12.5 times larger than a constantly-rewritten one and cost the same per turn. The trade has already fired the wrong way in a real run. On sw-6-ripple, a 60 kB interface-migration task, the tree arm rewrote an approximately 34,000-token prefix on each of its last four turns: 136,088 of the run's 161,938 cache-write tokens, 84% of its whole write bill, spent on four consecutive rewrites of content that had just been readable, while its cache reads collapsed to the 3,305-token frozen prefix. Removing the truncation budget that caused the churn brought median cache writes from 161,938 to 33,317 tokens over n=3 per arm, and the whole-run bill from 3.17 to 1.31 times the transcript baseline's, with turns unchanged at 12 and every replicate scoring 100%. On the second scenario in the same batch the same change moved cache writes the other way, from 35,547 to 53,191 tokens, so the fix is one scenario's win at n=3, not a general result. Two structural facts frame what to do next. The shipped request builder emits two of the provider's four allowed cache breakpoints and marks nothing on the active-branch detail, so that section is fresh input on every turn by construction, with a third breakpoint available and unused; the three-breakpoint builder that closes that gap exists only in an evaluation script behind an environment flag. And the cache assertion harness the implementation plan called for already exists — 612 lines of simulator, 574 lines of tests, 13 tests running offline in 101 ms, including one that catches a dropped breakpoint as a total loss of cache reads — and the request builder that produced every live number in this report has never been passed through it. The dimension's largest remaining measured token gap is on the read side, which the same rate ratio makes its cheapest: the open sw-3-refactor gap of 28,594 tokens at the median is 22 to 71 times cheaper per run than the write bugs already fixed, so the work it argues for is turn count, not caching.

1 Terms, rates, and where the numbers come from

A turn is one model call inside a run: the harness sends a prompt, the model answers, tool results come back, the next turn begins. A run is one arm attempting one scenario once; a replicate is one such run within a cell, and n is the number of replicates in the cell. An epoch is a batch of runs made in one sitting against one build, so two arms compared inside one epoch saw the same code, the same task material and the same model snapshot. Scores are reported as means, tokens and turns as medians, as in this program's other reports.

A breakpoint is a cache_control marker a request places after some content. The provider stores the byte prefix up to a breakpoint; on a later request it returns the longest previously cached prefix that still matches byte for byte, charging the matched part at the cache-read rate and any new content up to the next breakpoint at the cache-write rate. Content after the last breakpoint is fresh input at the plain input rate. A prefix invalidation is any edit that stops a later request's bytes from matching an earlier cached prefix at or before some breakpoint; it does not delete anything, it stops the read from reaching that far.

The prompt has three sections, fixed in order. Zone A is the frozen system contract and tool schemas. Zone B is one summary per completed branch, in creation order. Zone C is the full detail of the branch in progress. Retrieved results append after Zone C. A branch is a contiguous stretch of work on one sub-problem, which gets a summary when it closes.

Four rates are published in packages/core/src/models/cost.ts for claude-sonnet-5, the model behind every live number here: input, output, cache-read and cache-write, per million tokens. The two cache rates are fixed multiples of the input rate — cache-read is 0.1× input and cache-write is 1.25× (cost.ts:47-49), and claude-sonnet-5 is declared as tier(2, 10) at cost.ts:60. The ratio that matters is therefore cache-write ÷ cache-read = 12.5, exactly, and it is a property of the price table rather than of any measurement.

To state costs without dollars, this report uses one derived unit. A read-equivalent is the price of one cache-read token. In those units an input token costs 10, an output token 50, a cache-read token 1, and a cache-write token 12.5. Read-equivalents are a linear transform of the published rates, so a total in read-equivalents is convertible to money by one multiplication and is stated for the baseline in the footnote.† All token counts remain tokens.

The live numbers come from two committed batches on the same day, 1 September 2026: eval/results/long-v6x, which holds the native transcript baseline and the tree arm before the fix of §3, and eval/results/long-v64, the tree arm re-run after it. Each run file carries a per-turn record with the provider's own usage split, so the per-turn series in Figures 1 and 2 are read from disk rather than reconstructed. Every one of the nine runs behind Tables 1 and 2 has status completed and success true, verified per run; no cell here contains a harness-stopped run, and therefore no cell contains a zero that the harness fabricated in place of a real score. That distinction is not hypothetical in this repository — the transplant harness does score turn-capped runs as wrong answers (eval/plans/portability-audit/03-transplant.md:312) — but no figure in this report is drawn from that harness, which as §4 notes does not model provider caching at all.

2 The arithmetic that settles the central question

The question the dimension poses is whether it is better to keep a large prefix stable and read it every turn, or to keep a smaller one and accept that it is rewritten. The two rates answer it, and the answer is not close.

Let N be the size in tokens of some content that must be in the prompt every turn. Held stable and read, it costs N read-equivalents per turn. Rewritten every turn, the same content costs 12.5N. Rewritten once every k turns and read on the other k − 1, it costs N(12.5 + k − 1)/k = N(1 + 11.5/k) per turn, so the rewrite premium is 11.5N/k. That premium falls below the cost of merely reading the content — below N itself — only when k exceeds 11.5, which is to say when rewrites are rarer than about one turn in twelve. Turned around: a stable prefix of M tokens read every turn costs the same per turn as a churning prefix of N tokens rewritten every turn when M = 12.5N. Size is not the lever; rewrite frequency is.

This derivation is exact given the two constants, and it is only a derivation. Nothing in this repository varies rewrite frequency independently of prefix size to confirm it holds against real provider behaviour, and the simulator of §7 is deliberately built to consider only the previous submission's cache entries (packages/core/src/cache/simulator.ts:20-25: "under-crediting cache reads cannot hide a D5 regression; over-crediting could"). A real multi-entry cache under a time-to-live could in principle do better than these numbers, never worse.

3 The trade firing the wrong way, before and after

The mechanism is on record as a real regression, on sw-6-ripple: an interface migration touching ten dependent files, about 60 kB of material and a hidden test suite of 36 cases. Below a size threshold the tree runs in devolved mode, showing the whole trace instead of summaries on the argument that summarizing a short conversation costs money for nothing. That mode still applied a 30,000-token budget to the trace, and the truncation rule recomputed one shared per-block cap on every request. Each new tool result moved the cap by a token or two, which altered every already-truncated block at once, which invalidated the whole cached prefix. The fix removed the budget in devolved mode, whose stated contract was always to show the whole trace.

Figures 1 and 2 split the same three runs into their cache-read and cache-write series. Each figure carries the native transcript baseline from the same scenario, the same model and the same day, so the candidate is never shown alone.

Two arithmetic consequences of Figure 2 are worth stating in the units of §2. The four churning turns wrote 136,088 tokens, 84.0% of that run's entire 161,938-token cache-write bill, for content that was already cached; at 12.5 read-equivalents per write token that is 1,701,100 read-equivalents, against 116,193 for every cache read the whole twelve-turn run performed. Four turns of churn therefore cost 14.6 times the run's complete read bill. In the fixed run the corresponding four turns wrote 13,508 tokens (168,850 read-equivalents) and read 134,494.

4 Breakpoints: two of four in the shipped builder, three in the evaluation one

The Anthropic Messages API honours at most four cache_control breakpoints per request. That is not inferred here: it is asserted in three independent places in this repository — ANTHROPIC_PROFILE sets maxBreakpoints: 4 with a comment naming the constraint (packages/core/src/cache/simulator.ts:72-76), a comment on the native arm's own cache logic explains that mutating history "would accumulate markers past the provider's 4-breakpoint limit" (eval/src/loop.ts:352-353), and a test is titled for it (eval/test/loop.test.ts:252).

Two request builders exist, and they use a different number of the four.

The shipped library leaves two of four unused, and the unused third is worth something already measured. toCompletionRequest is what @context-tree/core exports and what the implementation plan's §10 rule 5 documents in full: "Emit cache-control breakpoints at the Zone A/B and B/C boundaries" (docs/IMPLEMENTATION_PLAN.md:419-421) — no third rule, no fourth. The three-breakpoint builder that reaches native-equivalent economics within a phase lives only in the evaluation script, behind an environment flag with no default, and has never been lifted into packages/core. What it bought when it landed is on record: median fresh input per turn fell from 2,400–7,600 tokens to 36–892 across the arm (reports/metrics/tree-vs-transcript.md:14,26,155). That is the same defect shape the portability audit names for the budget derivations — "sound but landlocked in an eval script" (eval/plans/portability-audit/03-transplant.md:330) — except that here the landlocked code has a measured saving attached rather than a hypothetical one.

The situation is worse than two of four for anything actually deployed. ZoneAssembler, the only thing that can emit even the two-breakpoint version, is never constructed inside packages/mcp; a grep for it across that package returns nothing, and the audit records the same result with its consequence spelled out (eval/plans/portability-audit/01-core.md:60). A host running @context-tree/mcp today gets zero breakpoints from the shipped server, because the server never assembles a prompt at all.

The fourth breakpoint is a different case, and calling it wasted would be wrong. With context-tool results folded into the event stream (EVAL_FETCH_EVENTS=1, eval/src/loop.ts:850-853), what remains after the third marker is the descendant map, which the code's own comment says must stay uncached because it grows with every edit — marking it would rewrite the whole zone at 12.5 read-equivalents per token for content that changes again next turn, which is precisely the mechanism ranked fourth in §5. The accurate statement is: two of four unused in the shipped path, which is a portability defect with a measured cost; one of four legitimately unused in the best path that exists, because nothing left in the prompt is stable enough to mark.

None of this is observable on the other providers this repository runs. fromOpenRouterResponse hard-codes cacheWrite: 0 (packages/core/src/models/openrouter.ts:208) with the reason in the file's own header: "There is no upstream cache-write counter, so cacheWrite is a reported zero. An unknown reported as zero is honest; a fabricated number is not" (openrouter.ts:9-10). Every rewrite claim in this report is therefore Anthropic-specific. The cross-model transplant harness confirms the same limitation from the other side: eval/scripts/transplant.mjs contains no reference to cache_control, a breakpoint, or a cache-write field anywhere, so its token comparisons are cache-agnostic by construction rather than by having found caching irrelevant.

Pricing either decomposition in read-equivalents makes the dimension's shape clear. The cross-day estimate's cache-read share is 93.5% of 98,006 tokens, about 91,636 tokens, which is 91,636 read-equivalents. The corrected 28,594-token residual, priced entirely at the read rate as its offline attribution implies, is 28,594 read-equivalents. Compare the first row of Table 4, where a write-side defect of comparable token magnitude — 161,938 tokens — cost 2,024,225 read-equivalents. The write bug was therefore 22 times the larger read estimate and 71 times the corrected one, while moving a comparable or smaller number of tokens, purely because of the 12.5× rate asymmetry.

The conclusion is narrow and worth stating carefully. The dimension's biggest published token gap is one of its cheapest in money, and the write bugs already fixed were each worth more while moving comparable or fewer tokens. That is not an argument that the sw-3 gap does not matter: tokens and turns are this program's primary metrics, and 1.71× native on tokens is still the open failing criterion. It is an argument about where the next unit of effort goes. A fix aimed at the sw-3 gap's cost would be solving the wrong problem; a fix aimed at its turn count addresses the one thing that is expensive in both metrics that count. The obvious mechanism there has already been refuted: calls per tool-using turn are 2.15–3.38 for the baseline and 2.25–3.20 for the tree, two-sided Mann-Whitney p = 0.81, and the earlier "2.77 against 1.49" that motivated the batching hypothesis came from three fast runs on a different day.

7 The instrument already exists, runs offline, and was not being used

The implementation plan asked for a "cache assertion harness: deterministic tokenizer + provider cache simulator asserting exactly which prefix ranges survive each event type — this is where D5 regressions will surface" (docs/IMPLEMENTATION_PLAN.md:593-595). It exists, committed, and the simulator's own header quotes that sentence back (packages/core/src/cache/simulator.ts:1-3).

The plan this report is based on stated 575 lines and about 19 tests; the reproduced figures are 574 lines and 13 tests, and the harness has a second caller in e2e.test.ts that the plan did not mention.

The specific zero-token test that catches a dropped breakpoint is cache.test.ts:441, named "reports a dropped §10 rule 5 breakpoint as total loss of cache reads even though every block is byte-identical". It takes an assembled prompt, strips every breakpoint flag while leaving every block byte for byte unchanged, and asserts that the surviving segment list becomes empty and cache reads become zero. That is exactly the failure the assembler's own doc comment warns about: "A caller that built a request from toMessages alone dropped the Zone A marker silently — nothing fails, the session just pays full price for the frozen prefix on every turn" (assembler.ts:404-407). Its positive control is cache.test.ts:185, which asserts that a byte-identical re-assemble is read from cache and that read plus write plus fresh always sums to the whole prompt — the conservation check that would catch a simulator bug pretending to be a clean result. A third test (cache.test.ts:488) proves that a prompt below Anthropic's 1,024-token floor caches nothing even when the layout is perfect.

The gap that matters is which builder the harness sees. Every test that submits to the simulator submits a prompt built by ZoneAssembler and the two-breakpoint path. toZoneCCachedRequest — the three-breakpoint builder through which every live number in this report actually ran — is never passed to ProviderCacheSimulator, assertPrefixStable or CacheAssertionError anywhere: a grep across eval/src, eval/test and eval/scripts returns no hits in any source file, only the source plan for this report and a recorded transcript fixture that happens to quote the test file. Its own coverage is three hand-written tests (eval/test/loop.test.ts:217-276) checking which messages carry a marker, that the count is three, and that earlier messages stay byte-identical after an append. That is real coverage of the right properties, but it is a second, independently written, less rigorous instrument watching the one request builder that matters for every measurement in this repository, while the general-purpose instrument built for exactly this job watches the builder that no live run uses. Concretely: an edit to toZoneCCachedRequest that reintroduced the map-churn defect of Table 4 row 4 would have to be caught by those hand-written assertions; the harness the repository describes as the place where such regressions surface "and essentially nowhere else" would not see it.

8 What is measured, and what is derived or hypothesised

Measured. Every token, turn, score and success count in Tables 1 and 2 and Figures 1 and 2, recomputed in this pass from the committed run files of long-v6x and long-v64 rather than quoted. The 84.0% churn share and the 14.6× comparison in §3, computed from the same per-turn arrays. Every breakpoint count in Table 3 and every line and test count in Table 6, read from committed source and, for the test count, from an actual test run. The per-turn signatures behind Table 4 rows 3 and 4, read from the iteration-4, iteration-5, iteration-6 and iteration-8 run files. Row 2's 223,917 tokens and 12 turns, read from the committed log. Both rows of Table 5, read from the item-3 plan, with the same-day row's arithmetic checked (68,634 − 40,040 = 28,594).

Derived. The 12.5 ratio and everything in §2 that follows from it, including the one-in-twelve break-even and the 12.5×-larger-prefix equivalence. These are exact consequences of two constants in the price table, not swept results: no experiment here varies rewrite frequency independently of prefix size, and the simulator is deliberately conservative about how much a real cache would credit. The read-equivalent unit and every total expressed in it are a linear transform of the published rates.

Hypothesis, and where the evidence is thin. That removing the devolved-mode budget is a general improvement is not established: it improved sw-6-ripple and worsened sw-5-dozen in the same batch, n=3 per cell, one model, one day, so what is established is that the mechanism is real and that one instance of it was expensive. That the correct target for further sw-3 work is turn count rather than caching is this report's synthesis of Tables 4 and 5 rather than a new experiment, although the item-3 plan reached the same conclusion by a different route. That the third breakpoint would pay in the shipped library is inferred from a measurement made inside the evaluation harness; nothing has yet measured it in packages/core, and nothing at all has measured it on a second provider, since no non-Anthropic provider in this repository reports a cache-write count.

One candidate parameter surfaces and should be refused as a parameter. The algorithm's third rule holds that setting a value from a model's limits is fine and guessing it is not. How many breakpoints the assembler emits is not a tunable at all: it is the smaller of the number of genuinely stable zone boundaries and the provider's own maximum, both of which the host reports. Generalising toZoneCCachedRequest's three boundaries and reading the maximum from a provider capability produces the number without anyone choosing it. No new constant is proposed here; the change §4 implies is moving existing, already-measured logic into the library.

9 Open items and recommendations

Ordered by expected information gained per unit of effort, where effort is counted in tokens and runs spent.

  1. Route toZoneCCachedRequest through ProviderCacheSimulator. Zero tokens, zero runs, one test file. It converts the §7 coverage gap into standing coverage of the one builder every live measurement uses, and it can encode Table 4's four fixed mechanisms as regression assertions instead of leaving them as history. Highest information per unit of effort in this dimension by a wide margin, because the instrument, the profiles and the assertion helpers already exist and run in 101 ms.
  2. Port the third breakpoint into packages/core, and assert its layout offline before spending a live run on it. Also zero tokens to validate: the simulator can show that Zone C's stable blocks move from fresh input to cache reads under the Anthropic profile, which is the whole claimed benefit. Only after that does a live batch have anything to confirm. This closes a defect whose cost is already measured (fresh input per turn 2,400–7,600 → 36–892) rather than assumed.
  3. Decide, in writing, whether the shipped MCP server is meant to assemble prompts at all. One grep of effort. Today it never constructs ZoneAssembler, so it emits zero breakpoints and the entire zone-assembly subsystem — including everything in items 1 and 2 — has no effect on any deployment that attaches it. Either the server should assemble, in which case items 1 and 2 become shipping fixes, or tool-backend mode is the product and this report's breakpoint findings are about the evaluation harness only. The ambiguity currently makes every caching claim in the repository harder to scope than it needs to be.
  4. State the simulator's single-entry conservatism as a bound, or model multi-entry caches. Offline, and cheap. The present model considers only the previous submission's entries, which cannot hide a regression but can understate a real cache's performance. Either extend it or record the direction of the bias where its outputs are quoted, so that a future comparison between simulated and billed numbers is interpretable.
  5. Settle the Table 1 versus Table 2 contradiction before the devolved-mode fix is described as an improvement anywhere else. This is the first item that costs real tokens: two scenarios, three arms, n ≥ 5, one epoch. It is ranked here rather than higher precisely because the write-side mechanism it would confirm has already been fixed, so the information bought is about generality rather than about a live defect.
  6. Spend no further live runs on the sw-3 gap's cost; spend them on its turn count, and only after an offline decomposition predicts a specific effect. The item-3 plan's own advice is not to raise n — the baseline alone spans 33,501 to 65,033 tokens over five runs, so an effect worth two or three thousand tokens per run cannot be resolved live at any affordable n. The gap decomposes deterministically from the per-turn records instead. Last in this list because it is the most expensive per unit of information, and because §6 shows the metric it would move is the cheapest one in the dimension.
