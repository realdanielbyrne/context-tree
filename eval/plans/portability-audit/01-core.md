# Portability audit — the algorithm itself (`packages/core`, `packages/mcp`)

This is one area pass of a portability audit against `reports/algorithm.md`, scoped to
the code that would actually ship to a new host: `packages/core/src/{assemble,
summarize, retrieve, ingest, store, prompts, models, providers, tokens, config.ts}` and
`packages/mcp/src`. `reports/algorithm.md` already lists seven hardcoded defects; this
report does not repeat those beyond confirming their exact locations, and adds what it
found beyond that list. Every claim below cites a `file:line`.

## Headline

The seven known hardcoded values are real and confirmed below, but they are symptoms of
one structural gap: **`packages/core` has no representation of the host's window size
(`W`) anywhere** — no field on `ContextTreeConfig`, no parameter on `ZoneAssembler`,
no exported function that takes a token budget in and returns a zone size out. Every
number in the tier-2 table that "should be a fraction of W" is a plain integer literal
for the same reason: there is nothing in the library to divide by. A caller can override
`zoneBBudget`/`zoneCBudget` per `assemble()` call, so the *capability* to be
host-sized exists at the API boundary — but nothing ships that computes those overrides,
so every real caller either hardcodes its own guess (as the defaults here do) or
reimplements the fraction math outside the library (as the eval harness's transplant
script does, per D19). A second, larger gap sits underneath that: the tier-1 "decide how
much to summarize" switch/latch step described in `reports/algorithm.md` — the whole
reason budgets would ever need to be W-relative — **does not exist as code in
`packages/core` or `packages/mcp` at all**. It lives only in `eval/src/loop.ts`, which is
explicitly out of scope for what ships (§ "Not part of the algorithm" in
`reports/algorithm.md`). A host that installs `@context-tree/mcp` today gets four
retrieval tools and a set of flat-numbered defaults; it does not get the switch-point
decision the reference description opens with.

## Dead or near-dead branches

- **`ZoneAssembler` is never constructed inside `packages/mcp`.** `grep -rn "new ZoneAssembler"` across the repo hits only test files and `eval/`. The MCP server (`packages/mcp/src/server.ts`) wires up `context_fetch`/`context_search`/`context_peek`/`annotate` and nothing else — it never calls `assemble()`. Concretely: **in the v1-default `tool-backend` mode (D14, D19 Q5), the entire `assemble/` subsystem — Zone A/B/C construction and every one of the hardcoded budgets above — has no live effect on any deployment that attaches this MCP server today.** It is exercised exclusively by `eval/src/loop.ts`'s simulation of what a hypothetical `middleware`-mode host would do. This reframes the "hardcoded Zone B/C budget" defects: fixing them changes eval scores, not yet any running system, because nothing runs the code they gate. Proof: `grep -rln "new ZoneAssembler" packages/ eval/` → only `packages/core/test/*.test.ts` and `eval/*`; zero hits under `packages/mcp/src` or `packages/core/src` (non-test).
- **`RetrievalProvider.hydrate()` / `ProviderRegistry.hydrate()` are unreachable from the product surface.** All four providers (`graft.ts:147`, `serena.ts:149`, `augment.ts:147`, `vector-provider.ts:53-69`) implement `hydrate`, and `registry.ts:91-95` exposes `ProviderRegistry.hydrate`. Nothing in `packages/mcp/src` calls it — `context-search.ts` returns `Candidate[]` (path/span/snippet pointers) and stops; `context-fetch.ts` reads through `TreeRetriever.fetchBranch`, never through a provider's `hydrate`. `grep -rn "\.hydrate(" packages/mcp/src packages/core/src` (non-test) → zero hits outside `registry.ts` itself. It is tested in isolation (`packages/core/test/providers.test.ts`, `retrieve.test.ts`) but never wired to a tool a model can call, so `DEFAULT_HYDRATE_MAX_CHARS`'s 64KB cap has never been exercised end to end.
- **The tier-1 switch/latch decision has no code in scope.** `grep -rln "switch point|switchPoint|LAZY_TOKENS|latch"` across `packages/core/src` and `packages/mcp/src` → zero hits. `grep -rn "process.env\."` across the same → zero hits outside `config.ts`'s API-key/`.env` loading. The "seven environment flags, all on" gate row and the switch-point threshold `reports/algorithm.md` marks hardcoded both live entirely in `eval/src/loop.ts`. Not a defect in this area's code — there is no defect, because there is no code. It is a scope gap: a host adopting `@context-tree/core` directly gets no switch-point implementation to even audit.

## Boundary conditions (breaks-first order)

| Condition | Checked today by | What happens when violated |
|---|---|---|
| Sum of `budgets.zoneB + budgets.zoneC` (38,000 tokens by default) exceeds the whole window | Nothing in `packages/core`. `assembler.ts:161-162` records `overBudget` in the *output* of `assemble()`, but only after building the oversized prompt — no guard rejects a config whose defaults can't fit any real host. `resolveConfig` (`config.ts:191-195`) validates only `> 0`, not any relationship to a window size, because no window size is ever supplied. | **Silent wrong answer, then a provider error two layers away.** The caller gets a prompt reported as `overBudget: ['B']` or `['C']` and can choose to send it anyway; if it does, the provider (Anthropic/OpenRouter) either 400s on context length or (worse) silently truncates server-side, and nothing in this codebase distinguishes "assembler said fine, provider truncated" from "assembler flagged it and we sent it anyway." |
| A branch's raw span, or a leaf's un-summarized detail, is larger than the window | Nothing. `retrieve/detail.ts:114-122` (`renderSpans`) and `summarize/detail.ts:78-100` (`renderBranchDetail`) have no aggregate cap; `INDEX_ROW_CAP=120` (`detail.ts:135`) caps only `depth:'index'`, not `depth:'full'`. `packages/core/test/live/contract.test.ts` is the only test that exercises `renderBranchDetail`, and it is `LIVE=1`-gated (opt-in, network-calling), so this path is untested in CI. | **Silent oversized payload.** `context_fetch` returns the whole thing in the tail (`assembler.ts:143-145` appends whatever text it's given, no truncation on tail entries); the leaf summarizer sends the whole thing to the cheap model. Neither path retries at a smaller scope on its own — the model has to notice and re-call with `depth:'index'` + `from`/`to`, which the tool description recommends (`context-fetch.ts:32`) but nothing enforces. |
| `retrieval.limit=20` results × `SNIPPET_CHARS=240` × full `SearchHitMeta` on a small window | Nothing computes the actual payload size against any budget; `reports/algorithm.md` records this was *measured* to overflow headroom in 8/15 runs at a 16k window, but that measurement lives in `eval/`, not as a guard in `packages/core`/`packages/mcp`. | Silent — the tool returns a valid, well-formed, oversized result; the calling harness's own context management (outside this codebase, since `assemble/` isn't in the loop for a real host per the dead-branch finding above) is what actually decides whether it fits. |
| `embedModel` is swapped for one with a different distance distribution (D8's stated supported operation) | Nothing. `RELATES_MAX_DISTANCE=0.35` (`enrich.ts:34`) does not move with `embedModel`, and no test asserts a relationship between the two. | Silent wrong answer: `relates_to` links become systematically over- or under-generated depending on whether the new embedder's typical same-topic cosine distance sits above or below 0.35 — enrichment is non-blocking (D15) so nothing surfaces this as a failure, the tree is just quietly less (or spuriously more) connected. |
| A host wants the switch/latch behavior `reports/algorithm.md` describes (raw trace until a threshold, then tree) | Nothing — the behavior does not exist in `packages/core`/`packages/mcp`. | Not a runtime failure (there is nothing to violate), but a host builder reading `reports/algorithm.md` as the spec for what `@context-tree/core` provides will not find this step and has to reimplement it, guessing at the threshold the same way the "hardcoded" live suite currently does. |
| Contract text needs to change per model (small model needs `v2`/`v3`) | Nothing — `createServer` (`server.ts:61`) always installs `v1`; `ContextTreeConfig` has no field for it. | Not silent — a host that wants `v2`/`v3` simply cannot get it without a code change to `packages/mcp/src/server.ts`, so this fails loud (missing feature) rather than wrong, but it means the "host, if a smaller model needs different instruction" row of `reports/algorithm.md`'s tier-2 table currently overstates what is actually configurable. |
| L1 schema version mismatch (a DB built by an older/newer `packages/core`) | **Checked and handled well** — `store/sqlite.ts:213-220` throws a named error telling the caller to delete and re-import, with no migration path attempted. Cited here as a contrast: this is what a correctly-guarded boundary looks like elsewhere in the same file the budget checks are missing from. | Loud failure, by design (D8: L1 is derived, never migrated). |

## Top three, if only three get fixed

1. Give `ContextTreeConfig`/`ZoneAssembler` an actual window-size input and one exported function that turns it into `{zoneA, zoneB, zoneC, tail, slack}` fractions (per D19's own allocation), so `DEFAULT_CONFIG.budgets`, `rootKeep`, and `retrieval.limit` stop being independent guesses and become one derivation with one thing to get right. This also gives the currently-nonexistent switch/latch step somewhere to live inside `packages/core` instead of only in `eval/src/loop.ts`.
2. Cap `renderSpans` (`retrieve/detail.ts`) and `renderBranchDetail` (`summarize/detail.ts`) against *something* — even a flat safety ceiling beats no ceiling — since these are the two paths with literally no upper bound today, and the leaf-summarizer one isn't in CI at all (`LIVE=1`-gated only).
3. Collapse the five peek/snippet/hydrate-size constants (800 / 2,000 / 2,000 / 240×3 / 65,536) into one shared, importable value, before deciding what that value should be.
