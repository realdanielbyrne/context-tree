# eval/fixtures — synthetic traces for the §15 benchmark

**Every trace in this directory is synthetic.** They are written in
`scenarios.ts` and `shapes.ts` and generated by `generate.ts`. Nothing here is
derived from a real Claude Code session, scrubbed or otherwise: a trace log is a
verbatim record of someone's private work, and scrubbing is never provably
complete. §17 of the plan says "recorded traces (real sessions, scrubbed)" — this
is a deliberate, stated deviation from that one line.

Each generated `.jsonl` says so in its own header, because the file will outlive
this README.

## Layout

| File | What it is |
|---|---|
| `build.ts` | `buildTrace()` — the fluent builder a scenario declares a session shape with, plus the canonical `.jsonl` serializer |
| `shapes.ts` | the seven session shapes §7's segmenter has to handle, as standalone fixtures |
| `scenarios.ts` | the 30 task traces, each with the phase sequence it must segment into and the golden file states it heads toward |
| `generate.ts` | writes the catalogue to `traces/` |
| `traces/*.jsonl` | the generated, committed fixtures a task's `trace.fixture` points at |

## The seven shapes

Each is asserted in `eval/tasks/tasks.test.ts`; a shape whose outcome nothing
asserts is a fixture that cannot fail.

| Shape | §7 clause it exercises |
|---|---|
| `shape-clean-progression` | one phase per activity kind, in order |
| `shape-read-dominated` | Ruling C6 — `other` is neutral, so reads and shells stay ONE branch. The test also runs the counterfactual with `neutralPhases: []` and shows it shattering |
| `shape-reedit-across-phases` | file nodes are phase-scoped, so a path edited before and after a test run owns two nodes |
| `shape-explicit-boundary` | a `segment_boundary` wins over the tool state machine |
| `shape-unmapped-tool` | §18 — an unmapped tool name degrades to `other` and is reported, never crashes |
| `shape-broken-edit` | §12/D9 — a syntactically broken post-edit file still yields spans |
| `shape-long-session` | §16 M1 — 408 events, one O(n) pass, under 5 ms, bit-identical |

## Determinism

No clock, no randomness, no cross-builder counters. `serializeTrace` writes a
fixed key order per event type rather than trusting object construction order,
and `tasks.test.ts` asserts that two generations are byte-identical **and** that
they equal the committed bytes. A fixture that is not byte-stable makes D8 — L1
and L3 are deterministic functions of L0 + L2 — untestable.

## Regenerating

```bash
node node_modules/.pnpm/vite-node@*/node_modules/vite-node/vite-node.mjs \
  --config vitest.config.ts eval/tasks/generate.ts -- --write
```

That rewrites `traces/` and the three task JSON files together, which is the
point: a task's `golden` has to agree with the edits in its trace, and they are
authored side by side in `scenarios.ts` for exactly that reason.

There is no npm script for it because `eval/` is not in the `tsc --build` graph
and this package adds no dev dependencies; `vite-node` comes with vitest, which
is already installed.
